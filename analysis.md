\# DarkWater Financial CTF — Analysis



\## 1. Objective



The objective of this investigation was to analyse a simulated phishing website, understand its browser-validation and data-collection mechanisms, inspect its network traffic, and develop a Python-based automation agent to reproduce the workflow using controlled test credentials.



\## 2. Initial Reconnaissance



I began by inspecting the website's HTML, JavaScript resources, and browser behaviour. The initial page displayed a session-validation message and loaded a JavaScript file responsible for controlling access to the simulated banking interface.



I also reviewed DNS and network activity to identify relevant external services and requests associated with the website.



\## 3. Browser Validation and Anti-Automation



Analysis of `worker.js` revealed several browser checks designed to identify automated or suspicious browsing environments. These included checking `navigator.webdriver`, browser properties, plugins, languages, window dimensions, and automation-related indicators in the DOM.



The script used two cookies to manage access:



\- `darkwater\_access\_blocked` — indicated that access had been blocked.

\- `darkwater\_access\_verified` — indicated that browser validation had succeeded.



Depending on the validation outcome, the browser was redirected to `/blocked` or `/landing`. This demonstrated how client-side browser checks and session state controlled access to the simulated login interface.



\## 4. JavaScript and Login Workflow Analysis



I examined `login.js` to understand what happened when a user submitted the login form.



The script collected the submitted username and password, then queried the GeoJS service for contextual information. The returned metadata could include IP address, city, region, country, coordinates, timezone, organisation, and ASN.



The script combined the submitted credentials and available metadata into a JSON payload. This indicated that the login workflow was collecting more information than would ordinarily be necessary to display a basic authentication error.



\## 5. Network Traffic Analysis



Using browser developer tools, I inspected the requests generated by the login workflow.



Two requests were particularly relevant:



\- \*\*GeoJS:\*\* Retrieved IP and geographic/network metadata.

\- \*\*`/session`:\*\* Received a GET request containing a custom `X-Payload` header.



The login script serialised the collected information as JSON, encoded it using Base64 twice, and transmitted it through the custom header.



The `/session` response indicated that the browser had passed the server-side session check. Following submission, the interface displayed an "Invalid credentials. Please try again" message.



The discrepancy between the user-facing error and the underlying network activity was an important finding.



\## 6. Payload Analysis



I inspected the `X-Payload` header and decoded it twice to recover the underlying JSON structure.



The decoded payload contained the submitted test credentials, a timestamp, and available IP, geographic, and network metadata.



This validated the behaviour observed in the JavaScript and demonstrated how the website collected and transmitted the information associated with the simulated login attempt.



Base64 encoding provided an encoding mechanism, not encryption or confidentiality.



\## 7. Python Automation



I developed a Python agent using Playwright to automate the investigation.



The agent was designed to:



1\. Launch a Chromium browser.

2\. Navigate through the website's browser-validation workflow.

3\. Open the simulated login page.

4\. Submit controlled test credentials.

5\. Capture the `/session` request.

6\. Extract and decode the `X-Payload` header.

7\. Redact sensitive values before saving evidence.



The agent successfully reproduced the workflow and captured the payload. This provided an automated way to validate the findings rather than relying solely on static code analysis.



\## 8. Technical Challenges



During implementation, I encountered and resolved several environment and automation issues:



\- Configuring Python virtual environments and dependencies.

\- Troubleshooting Kali Linux package-manager and repository-signing issues.

\- Installing missing Chromium system libraries.

\- Investigating the website's automation-detection behaviour.

\- Validating that the captured payload matched the behaviour observed in the JavaScript.



These challenges provided practical experience in Linux troubleshooting, browser automation, and iterative investigation.



\## 9. Key Findings



The investigation established that:



\- Browser-validation logic controlled access to the simulated banking interface.

\- JavaScript collected submitted credentials and contextual metadata.

\- GeoJS was used to enrich the collected information.

\- The payload was double Base64-encoded and transmitted in the `X-Payload` header to `/session`.

\- The interface displayed an authentication error despite the underlying data-collection workflow.

\- Combining JavaScript analysis, network inspection, and Python automation provided a clearer understanding of the website's behaviour than inspecting any one source independently.



\## 10. Conclusion and Lessons Learned



This CTF demonstrated the importance of correlating client-side code, browser behaviour, and network telemetry when investigating a suspicious website.



Rather than relying on the page's appearance or error messages, I followed the workflow from initial reconnaissance through to payload capture and decoding. Automating the process with Python and Playwright allowed me to reproduce the behaviour and validate my findings.



The project strengthened my practical skills in phishing investigation, JavaScript analysis, HTTP traffic inspection, payload decoding, Python automation, and technical troubleshooting.
